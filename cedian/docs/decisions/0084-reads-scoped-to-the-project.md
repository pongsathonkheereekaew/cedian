# ADR-0084: The agent's read tools see the project; anything outside asks, protected paths are denied

- **Status:** Accepted (owner, 2026-10-15, ADR-0077 decision 4 is the rule; the mechanism below is the agent's design, taken as the default)
- **Date:** 2026-10-16
- **Rule text:** fork `packages/coding-agent/src/tools/read-scope.ts` (`tools.readScope`: `readScopeDecision` is the argument check, `readScopeGrant`, `resultFilter` and `enforceReadScope` the result check), `crates/cedian_omp/src/spawn_profile.rs` (`ReadScope`, `READ_TOOLS`), `crates/cedian_shell/src/launch.rs` (`read_scope`), Settings > Permissions
- **Implements:** ADR-0077 decision 4
- **Builds on:** ADR-0012 (strict-wins, protected metadata paths), ADR-0020 (the spawn overlay), ADR-0035 (`policy = "omp"`), ADR-0044 (state outside the workspace), ADR-0075 (the narrow fork)

## Context

OMP's `read`, `grep`, `glob`, `find`, `ast_grep` and the read half of `lsp` declare the `read` tier, which every approval mode auto-approves, so the agent reads any file the person can. ADR-0077 decided reads are scoped to the project and anything outside asks. SET-4 stored the folders the person allows ahead of time (`[projects."<path>"] read_folders` in the user's `cedian.toml`, read through `Settings::read_folders_for`) and the Safe actions tier, but nothing applied either.

Two places could check a path. OMP sees it first, in each tool's `approval(args)`, before the call runs; cedian sees it only once OMP raises a dialog, and never for a call OMP auto-approved. A check in cedian alone would have to intercept every read call over RPC, which the protocol does not offer, so the check lives in the fork and cedian's gate stays the one that asks and audits.

## Decision

1. **The fork checks, cedian asks.** A new setting, `tools.readScope`, carries the scope into the agent through the spawn overlay (ADR-0020). The check has two layers (decision 4): each read tool's `approval(args)` judges what the argument names and returns the decision the resolver already understands (a tool `deny`, the plain `read` tier, or a forced prompt with the path in the reason), and the tool judges again, while it runs, every path it produces or opens. With no `tools.readScope` configured the tools behave as upstream, so the fork's CLI and its tests are unchanged.
2. **The shape.**
   ```yaml
   tools:
     readScope:
       roots: ["/Users/me/src/app"]        # the project; reads inside pass
       allow: ["/Users/me/src/shared"]     # read_folders from the user's cedian.toml
       protectedNames: [".git", ".cedian", ".omp"]   # denied under any root or allowed folder
       protectedPaths: ["/Users/me/.omp", "<agent config dir>", "<agent state dir>", "<cedian state dir>"]
       outside: prompt                     # or allow
   ```
   cedian writes `roots` as the canonical workspace, `allow` from `read_folders_for(workdir)` (the user's file only; a repository cannot widen its own scope), `protectedNames` and `protectedPaths` from `ProtectedRoots` (ADR-0012, ADR-0044, ADR-0078), and `outside: prompt`.
3. **Order of evaluation**, per path, strictest first (ADR-0012):
   1. protected: a component named in `protectedNames` under any root or allowed folder, or a path under a `protectedPaths` entry, is a tool `deny`. It is denied even inside an allowed folder, and the prompt never opens, so it cannot be clicked through.
   2. inside a root: `read`.
   3. inside an allowed folder: `read`.
   4. otherwise `outside` applies: `prompt` forces a dialog that names the path, `allow` passes.
   The user's `tools.approval.<tool>` is consulted after the tool's decision, so the Safe tier below can tighten but never loosen this: `allow` does not skip the outside prompt, `deny` and `prompt` apply to every read.
4. **Two layers: the argument check fails closed, the result check is the boundary.** Two rounds of review showed that predicting from an argument what a tool will open does not hold: the tools split lists in several modes, take URL shapes for paths, fall back to a workspace-wide suffix search, and walk directories the argument never named. So the check no longer predicts.
   - *The argument check* (`approval(args)`, before the call runs) resolves each entry with the tool's own functions (`toPathList`, the hashline unwrap, quotes, `expandPath` for the stray `:` prefix, `@`, `file://` and `~`, `resolveToCwd`). An entry that exists as written (with or without its `:N-M` selector) is judged as that path and nothing else, so a real `My File.md`, `a, b.txt` or `notes ~draft.md` inside the project does not ask. An entry that does not exist and holds a top-level `,`, `;`, whitespace or newline, or looks like a URL by any predicate a tool uses (`http(s):/`, `www.`, `scheme://`, a `scheme:/` alias), is not split or parsed: it forces the outside prompt, naming the entry. A URI of a scheme registered with the internal URL router keeps its own tier (its handler bounds it, decision 12), unless it carries a delimiter, which also forces the prompt. A remaining single entry is judged by the path it spells; a glob by the base it walks from, with a tail that could reach past the base (`..` after the first wildcard, a brace holding a separator or `..`) treated as outside and a protected name anywhere in the pattern denied. The prompt's answer is a grant for this call: the scope, plus the outside paths the argument named.
   - *The result check* (while the tool runs) judges every path again, canonical: the longest existing prefix through `realpath`, the rest appended, the roots and folders canonicalized the same way, so a symlink inside the project that points outside is outside. The existing prefix compares as the filesystem spells it; only the part that does not exist yet compares without case on macOS and Windows. `grep`, `glob`, `ast_grep` and `find` drop every produced path that is protected, and every path outside the scope unless it lies under an outside path the call was approved for (an approved outside walk root keeps only its own subtree). The native walkers take no exclude list, so the filter runs on their output; they never follow directory symlinks, and a symlinked file resolves outside and is dropped. `read` re-judges the file it finally opens, after every fallback (a delimited part, the unique-suffix search, the approved-plan alias, an archive, sqlite, JSON or binary resolution): protected is refused, and outside without a grant is refused with a message telling the model to call `read` with that explicit path, which asks. Nothing in the check rests on the glob engine's expansion rules.
   - A tool with no path argument searches the cwd, which is inside.
5. **Which tools.** `read` (text, images, PDFs, archives), `grep`, `glob`, `find`, `ast_grep`, and `lsp` for its read-only actions, through one helper. `edit`, `write` and `ast_edit` echo what they open (an edit of `.git/config` returns its lines), so they run the protected deny too, before their own write-tier prompt; outside the project they keep that prompt, which already asks. `bash` keeps its own approvals (ADR-0077 decision 4; ADR-0012's patterns). Out of scope, stated: `debug`'s read-only actions (`threads`, `stack_trace`, `variables`, `disassemble`) read a process the agent launched under the exec tier, not files, so the exec approval covers them; `lsp`'s `workspace_symbols`, `references` and `definition` return index entries the language server built, which can name files outside the project. A read of such a file is still a `read` call and asks. The index text itself is accepted as the cost of a working language server.
6. **The Safe actions tier applies.** `permissions.safe` in `cedian.toml` maps onto `tools.approval.<tool>` for every tool in `READ_TOOLS`: `ask` writes `prompt` (every read asks, inside the project too), `deny` writes `deny` (the agent cannot read), `allow` writes nothing. Under `policy = "omp"` only the `deny` survives, as for every other tier (ADR-0035 decision 3).
7. **Under `policy = "omp"`** (ADR-0035) the overlay still carries the scope with `outside: allow`: protected paths stay denied (a cedian deny applies in every mode), and whether an outside read asks is the person's OMP config's call, as every other approval is there.
8. **Asked once per call, audited.** The prompt is OMP's ordinary approval dialog (`Allow tool: read`, `Reason: outside the project`, `Path: …`), so the app shows it in the panel like any approval, and the answer lands in `audit.jsonl` as the gate row cedian already writes (tool, label, decision, who answered). A protected deny is audited by the fork's tool result; cedian's gate also refuses a dialog whose title names a protected path, as it does for writes.
9. **A read folder is never the project or its ancestor.** The settings writer and the loader share one predicate (`contains_project`, both sides canonical): the writer refuses such a `read_folders` entry, the loader drops a hand-edited one with a note (`["/"]` and `["~"]` included), and the Permissions and Projects pages show the refusal on the row. A `cedian.toml` found inside the open workspace is reported on both pages (`SettingsError::InWorkspace`), not silently ignored.
10. **The host's scope is the host's.** The spawn overlay is a `--config` layer, which the agent merges above the project's `.omp/config.yml`, so a repository cannot widen `allow` or flip `outside`. A `cfg://` write to `tools.readScope`, `tools.approval` or `tools.approvalMode` is refused while the overlay supplies them, so a session cannot loosen the scope it runs under, nor switch itself to `yolo` to skip the outside prompt. If `AgentDirs::from_env()` fails, the launch is refused rather than started without the agent's config dir in `protectedPaths`.
11. **What the check does not do.** The result check judges a path just before the open; a symlink swapped between that judgment and the open (TOCTOU) is not caught. Swapping one takes a write or an exec in the project, which the gate approves or denies on its own, so the window needs an approved mutation first. Under OMP's `yolo` approval mode a forced prompt is ignored, so an outside read passes, and the result check treats the outside paths the argument named as granted; a protected deny holds in every mode, and cedian never spawns the person's agent in `yolo`. An `http(s)` URL asks under a scope, since the same shape can name a path on disk; the fetch itself is unchanged once approved. A walk that drops results says nothing about them in its output.
12. **Internal URL schemes bound themselves.** `local://`, `memory://`, `vault://` and `skill://` resolve a URL under a root and refuse, with `realpath` on the root, the parent and the target, anything that escapes it (`ensureWithinRoot`, `containedRealPath`); `artifact://` and `agent://` pick a file by id from a directory listing, never from a path in the URL; `xd://` dispatches a device, not a file; `cfg://` reads the settings schema's values; `proc://`, `history://`, `attachment://`, `conflict://`, `omp://`, `issue://`, `pr://`, `ssh://` and MCP resources read process output, session records, documentation or remote data. These roots are the agent's own state (session artifacts, memory, skills) under the agent dirs that `protectedPaths` keeps from the filesystem tools: the handlers are how the agent reads its own files, and they are the only way. A traversal in one of them is a bug in that handler, not a gap in the scope. `image_gen`'s input path is a write-tier call and asks as such.
## Consequences

- The agent reads the project and the allowed folders without a dialog; the first read anywhere else is a question in the panel. A person who finds the questions tiresome adds the folder on Settings > Permissions, where SET-4 put it.
- `.git`, `.cedian` and `.omp` under the project or an allowed folder are unreadable by the agent, as are `~/.omp` and cedian's own agent and state dirs. A workflow that needs the agent to read git metadata goes through `bash` and its own approvals.
- The fork gains one setting and one module; upstream merges touch the six tools' `approval` properties and the point where each walker collects its results. Each tool test in the fork covers its own tier; the scope matrix is tested once on the helper, and the enforcement suite runs the tools against a fixture with symlinks, hidden metadata and delimited names.
- A read of a non-existing path that holds a space or a comma, or a URL, asks even inside the project. The question names the entry and says why; the person who adds the folder on Settings > Permissions is not helped here, since the path is the project's. This is the cost of not predicting.
- The read half of `lsp` asks when the file is outside; its write actions already did.
- Subagents (`task`) run headless under `yolo`; a read that resolves to `prompt` there is rejected, as every prompt is (approval-mode.md "Subagents"). A protected deny holds there too.
- The reviewer (ADR-0043) runs under Seatbelt and gets no `tools.readScope`: the kernel already bounds what it reads.
